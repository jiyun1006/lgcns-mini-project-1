## 한 줄 요약

**로그인·회원가입·아이디 찾기·비밀번호 찾기는 Spring 인증 서버와 실제로 연결됐다. 로그인한 사람은 MongoDB `User`와 이메일로 이어지고, `getCurrentUser()`는 로그인 세션 기준으로 사용자를 돌려준다(로그인 안 했으면 `null`). 마이페이지는 비밀번호 변경·로그아웃까지 실제로 동작한다. 남은 것은 `loginId` 중복 금지(DB 담당), 소셜 로그인 등 선택 기능이다.**

## 2. DB와는 어떻게 붙어 있나

**회원 정보는 두 곳에 나뉘어 있다.**

| 저장소                    | 들어 있는 것                                                                        | 우리가 만지는 방법                                |
| ------------------------- | ----------------------------------------------------------------------------------- | ------------------------------------------------- |
| Spring 인증 서버 DB       | 이메일, **비밀번호(해시)**, 이름, 숫자 `userId`                                     | API로만 (로그인·가입·비밀번호 찾기·비밀번호 변경) |
| 우리 MongoDB Atlas `User` | 이메일, 닉네임(`name`), `loginId`, 복구용 이메일, 관심사, 사진, 자기소개, 공개 설정 | Prisma로 직접                                     |

- 두 곳은 **가입 이메일**로 이어진다. 그래서 가입 이메일은 바꾸지 않는다.
- 채팅·게시판·마이페이지는 **우리 MongoDB의 `User` 번호(ObjectId)**로 "누가 썼나"를 기록한다. 인증 서버의 숫자 `userId`는 쓰지 않는다. (팀 합의: `user.id` = Mongo ObjectId)
- "지금 로그인한 사람"은 공용 함수 `lib/current-user.ts`의 `getCurrentUser()`가 정한다. 세션의 번호로 MongoDB `User`를 찾고, 로그인 안 했거나 그 회원이 없으면 `null`이다.
  - 채팅 API(`/api/chat`, `/api/conversations`)는 `null`이면 401을 돌려준다.
  - 마이페이지는 `null`이면 `/login`으로 보내고, 저장 액션은 "로그인이 필요해요."를 돌려준다.
- 게시판 API는 `lib/board/server-user.ts`의 `boardUser()`로 같은 방식의 확인을 한다. **글 목록·상세는 비회원도 볼 수 있고**(사용자 `null`), 글·댓글·좋아요 저장은 로그인하지 않으면 401이다.
- 출입증(세션)은 유효한데 MongoDB에 그 회원이 없으면(예전 로그인 쿠키, DB 변경) 화면이 자동으로 로그아웃시킨다(`StaleSessionSignOut`). 다시 로그인하면 정상이 된다.
- 프로젝트에 Cache Components가 켜져 있어서, 쿠키·세션을 읽는 곳은 `<Suspense>` 안에 두거나 `connection()`으로 요청마다 새로 조회한다.

## 3. API는 어떻게 보내고 있나

**브라우저가 인증 서버에 직접 가지 않는다.** 화면 → 우리 Next 서버(NextAuth, 서버 액션) → Spring 인증 서버 순서로 간다.

- 인증 서버 주소는 `.env`의 `NEXT_PUBLIC_API_URL`, 경로는 `config/apiuri.ts`에 모은다.
- 호출은 `lib/fetchClients.ts`의 `springFetch`로 한다. 응답은 항상 `{ success, message, data }` 모양이다.
- 화면은 `service/auth/authApi.ts`라는 **한 곳**만 부른다. 지금은 진짜(`realAuthApi`)가 꽂혀 있다. 가짜(`mockAuthApi`)는 서버 없이 화면을 시험할 때 쓴다.
- 인증 서버 토큰이 필요한 호출(비밀번호 변경, 로그아웃)은 서버에서 `lib/springToken.ts`로 세션 쿠키 안쪽의 토큰을 꺼내 쓴다.

사용하는 Spring 인증 서버 API (테스트 서버 Swagger에서 확인):

| 기능             | 요청                                                     | 쓰는 곳                              |
| ---------------- | -------------------------------------------------------- | ------------------------------------ |
| 로그인           | `POST /api/v1/auth/login` `{ email, password }`          | NextAuth `authorize`                 |
| 회원가입         | `POST /api/v1/auth/register` `{ email, name, password }` | `signupAction`                       |
| 이메일 중복 확인 | `POST /api/v1/auth/check-email` `{ email }`              | `checkEmailAction` (회원가입 2단계)  |
| 비밀번호 찾기    | `POST /api/v1/auth/password/forgot` → `password/reset`   | `passwordActions` (`/find-password`) |
| 비밀번호 변경    | `POST /api/v1/users/me/password` (Bearer 토큰)           | 마이페이지 `changePassword`          |
| 로그아웃         | `POST /api/v1/auth/logout` (Bearer 토큰)                 | NextAuth `events.signOut`            |

- Swagger 확인 결과: 가입 200 / 같은 이메일로 다시 가입 409 `CONFLICT` / 로그인 200 / 틀린 비밀번호 401 `UNAUTHORIZED`
- 보안키 메일은 인증 서버에 메일 설정이 있을 때만 실제로 간다. 테스트 서버는 응답에 `demoToken`을 같이 주지만 화면에는 띄우지 않는다.
- 비밀번호는 인증 서버만 보관한다. 우리 MongoDB·쿠키·localStorage 어디에도 두지 않는다.

필요한 환경변수 (`.env`, git에 올리지 않는다):

| 이름                  | 쓰는 곳                                                                                                      |
| --------------------- | ------------------------------------------------------------------------------------------------------------ |
| `NEXT_PUBLIC_API_URL` | Spring 인증 서버 주소                                                                                        |
| `NEXTAUTH_SECRET`     | 로그인 팔찌(JWT) 서명. **`AuthShell`이 루트 layout에 있어서 모든 페이지가 이 값을 쓴다. 없으면 에러가 난다** |
| `NEXTAUTH_URL`        | 우리 앱 주소 (로컬은 `http://localhost:3000`, 배포는 https 주소)                                             |

## 4. 로그인과 백엔드는 어떻게 연결되나

1. 로그인 화면 → `signIn("credentials")` → NextAuth `authorize`가 Spring 인증 서버에 로그인 (아이디로 넣었으면 먼저 MongoDB에서 가입 이메일을 찾는다)
2. 성공하면 **같은 이메일의 MongoDB `User`를 찾고, 없으면 만든다** (`upsert`). 새 사용자에게는 이메일 앞부분으로 `loginId`를 자동으로 붙인다. 같은 사람이 동시에 처음 로그인해서 중복 오류(`P2002`)가 나면 한 번 더 시도한다
3. 그 사용자의 ObjectId를 로그인 팔찌(JWT, 2시간)에 적어 쿠키로 둔다. 인증 서버 토큰은 팔찌 안쪽에만 두고 브라우저 JS에는 주지 않는다
4. `getCurrentUser()`가 팔찌의 번호로 MongoDB `User`를 찾는다
5. 로그아웃하면 팔찌를 지우고, 인증 서버에도 토큰을 그만 쓰겠다고 알린다

⚠️ **가입 이메일은 바꾸지 않는다**: 이메일은 인증 서버와 우리 MongoDB를 잇는 열쇠다. 인증 서버에는 이메일을 바꾸는 API가 없어서, MongoDB 이메일만 바꾸면 다음 로그인 때 사용자가 **새로 만들어져 데이터가 갈라진다.** 그래서 마이페이지에서 가입 이메일은 읽기 전용이고, 바꿀 수 있는 "복구용 이메일"을 따로 두었다.

## 6. 화면 구성 (간단히)

- 로그인·회원가입 컴포넌트는 `components/auth/` 아래 `atoms`(Button, Alert, LoginStatus 등) → `molecules`(TextField, PasswordField, TagInput, LoginRequiredNotice 등) → `organisms`(LoginForm, SignupForm, FindIdForm, FindPasswordForm, 회원가입 단계 화면) → `providers`(AuthShell, AuthProvider)로 나눴다. 디자인은 팀 목업 기준이고, 색·글자 크기는 아직 하드코딩이다
- 마이페이지는 위에서부터 **프로필·기본 정보 → 자기소개·관심사 → 공개 설정 → 비밀번호 변경 → 로그인 관리(로그아웃) → 내 활동 → 회원탈퇴**, 컴포넌트는 `components/mypage/` 아래 atoms → molecules → organisms → templates
- 포인트 색상은 게시판과 같은 버건디(`#A50034`)

## 참고: 겪었던 문제

- **DB 접속 실패(DNS 에러)**: `.env`의 클러스터 주소 오타가 원인이었다. 이런 에러가 나면 먼저 주소 철자부터 확인한다.
- **브랜치를 바꾼 뒤 빌드 실패(`tw-animate-css`를 못 찾음)**: 예전 브랜치에서 남은 빌드 캐시가 원인이었다. 브랜치를 바꾼 뒤에는 `npm install`을 하고, 그래도 안 되면 `.next` 폴더를 지운다.
- **커밋했는데 파일이 계속 "M"으로 보임**: 줄끝 문자(LF/CRLF) 차이라 내용은 같다.
- **스키마를 바꿨는데 `Unknown argument`**: 개발 서버가 예전 Prisma 도구를 들고 있었다. 서버를 껐다 켜면 된다.
- **`npx prisma generate`가 `EPERM`**: 개발 서버가 Prisma 파일을 쓰고 있어서다. 서버를 끄고 다시 한다.
- **로그인했는데 채팅·마이페이지가 `null`**: 예전 로그인 쿠키(세션 번호가 MongoDB 번호가 아니던 때)가 남아 있었다. 로그아웃 → 다시 로그인으로 풀린다. 지금은 자동으로 로그아웃된다.
- **머지 뒤 `package-lock.json`이 깨짐**: PR #28 머지 때 충돌 정리가 덜 됐다. 다른 팀원이 수습했다.

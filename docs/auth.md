# 인증 · 마이페이지 진행 상황

> 마지막 업데이트: 2026-11-11 14:28 / 브랜치 `feat/mypage-required`

## 한 줄 요약

**마이페이지는 우리 MongoDB에서 사용자 정보를 읽어와 보여주는 단계까지 됐다. 로그인은 아직 없어서 "DB의 첫 번째 사용자"를 로그인한 사람으로 간주하고 있고, 수정·업로드·비밀번호 변경·로그아웃은 화면에서만 동작하며 서버로 보내는 요청은 하나도 없다.**

## 1. 현재 상태

| 기능                         | 화면                   | DB 연결    | 비고                               |
| ---------------------------- | ---------------------- | ---------- | ---------------------------------- |
| 내 정보 조회 (닉네임·이메일) | 완료                   | **연결됨** | DB에서 읽어서 표시                 |
| 아이디·프로필 사진 표시      | 완료                   | 미연결     | DB 스키마에 해당 필드가 없어 빈 값 |
| 프로필 수정                  | 완료                   | 미연결     | 저장해도 새로고침하면 원래대로     |
| 프로필 사진 업로드           | 미리보기만             | 미연결     | 파일 저장소 미정                   |
| 비밀번호 변경                | 입력 검증만            | 미연결     | 서버 확인 없음                     |
| 로그아웃                     | 로그인 페이지로 이동만 | 미연결     | 세션이 없어서 지울 것도 없음       |
| 로그인                       | 껍데기 페이지만 있음   | 미연결     | `/login`에 "Login" 글자만 있음     |

## 2. DB와는 어떻게 붙어 있나

**API를 거치지 않고, 마이페이지가 서버에서 직접 DB를 조회한다.**

- 마이페이지는 서버에서 실행되는 페이지라서, 브라우저가 따로 API를 부르지 않는다. 페이지를 열면 Next 서버가 Prisma로 MongoDB에 바로 물어보고, 결과를 화면에 담아 내려준다.
- DB는 로컬이 아니라 **MongoDB Atlas(클라우드)** 다. 접속 주소는 각 폴더의 `.env` 안 `DATABASE_URL`에 있다. `.env`는 git에 올라가지 않으므로 폴더(워크트리)마다 따로 넣어줘야 한다.
- "지금 로그인한 사람"은 공용 함수 `getCurrentUser()`가 정한다. **현재는 DB에 있는 첫 번째 사용자를 그냥 돌려준다.** 채팅 API도 같은 함수를 쓰므로, 로그인이 붙으면 이 함수 하나만 바꾸면 마이페이지와 채팅이 함께 실제 사용자 기준으로 바뀐다.
- DB 값은 이렇게 화면에 연결된다.
  - DB의 `name` → 화면의 닉네임
  - DB의 `email` → 화면의 이메일
  - 아이디·프로필 사진 → DB에 칸이 없어서 비어 있음. 보이게 하려면 User 스키마에 필드를 추가해야 한다.
- 이 프로젝트는 Next의 Cache Components 설정이 켜져 있다. 그래서 그냥 두면 빌드할 때 한 번 조회한 값이 굳어버린다. 마이페이지는 **요청이 올 때마다 새로 조회하도록** 처리해 두었다.
- 현재 DB에는 테스트 사용자 1명(`test@test.com`)이 있고, **비밀번호가 비어 있는 계정**이다.

## 3. API는 어떻게 보내고 있나

**지금 마이페이지에서 서버로 보내는 API 요청은 없다.** 버튼은 모두 화면 안에서만 처리하고 끝난다. 각 버튼 코드에 "API가 생기면 여기서 호출" 표시(`shortcut:` 주석)를 남겨 두었다.

앞으로 붙일 API (로그인한 사용자 기준):

| 기능          | 요청                     | 보낼 내용                  | 실패 시                    |
| ------------- | ------------------------ | -------------------------- | -------------------------- |
| 프로필 수정   | `PATCH /api/me`          | 닉네임, 아이디, 이메일     | 아이디·이메일 중복이면 409 |
| 사진 업로드   | `POST /api/me/avatar`    | 이미지 파일                | 이미지가 아니면 400        |
| 비밀번호 변경 | `PATCH /api/me/password` | 현재 비밀번호, 새 비밀번호 | 현재 비밀번호가 틀리면 401 |
| 로그아웃      | `POST /api/auth/logout`  | 없음                       | 세션 쿠키 삭제             |

- "새 비밀번호 확인" 칸은 화면에서만 비교하므로 서버로 보내지 않는다. 길이 같은 규칙은 서버에서도 다시 검사해야 한다.
- 비밀번호는 해시(bcrypt 등)로 저장한다. 소셜 로그인 사용자는 비밀번호가 없으므로 변경을 막거나 카드를 숨긴다.

## 4. 로그인과 백엔드는 어떻게 연결되나

**현재는 연결돼 있지 않다. 강사님 API로 로그인해도, 그 결과가 우리 DB의 사용자와 자동으로 이어지지 않는다.**

- 강사님 API와 우리 MongoDB는 서로 다른 저장소다. 강사님 API에서 받지 않는 정보(관심사, 채팅 기록, 게시글 등)는 우리 DB에 따로 저장한다.
- 그래서 로그인을 붙일 때 아래 연결 고리를 직접 만들어야 한다.
  1. 강사님 API로 로그인에 성공하면, 그 사람을 **우리 DB의 User와 짝지을 기준**이 필요하다. 예를 들어 이메일로 찾고, 없으면 새로 만든다.
  2. 짝지은 사용자를 세션이나 쿠키에 기억시킨다.
  3. `getCurrentUser()`가 "첫 번째 사용자" 대신 세션에 기억된 사용자를 돌려주게 바꾼다.
- 이 세 단계가 끝나야 마이페이지·채팅·게시판이 진짜 "내 정보" 기준으로 동작한다. 로그아웃은 2번에서 만든 세션을 지우는 일이다.

## 참고: 겪었던 문제

- **DB 접속 실패(DNS 에러)**: `.env`의 클러스터 주소 오타가 원인이었다. 이런 에러가 나면 먼저 주소 철자부터 확인한다.
- **브랜치를 바꾼 뒤 빌드 실패(`tw-animate-css`를 못 찾음)**: 예전 브랜치에서 남은 빌드 캐시가 원인이었다. 브랜치를 바꾼 뒤에는 `npm install`을 하고, 그래도 안 되면 `.next` 폴더를 지운다.
